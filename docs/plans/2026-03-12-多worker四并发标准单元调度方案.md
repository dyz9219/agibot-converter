# 2026-03-12 多 Worker 四并发标准单元调度方案

## 1. 背景

当前性能测试已经证明：

- 单任务在优化后可以压到 `10s` 以内
- 但多任务并发时，单任务时延会随着并发数升高而显著上升
- 当前的 `8`、`16` 并发并不是把机器更高效地用起来，而是把更多完整任务同时压进同一个资源池

真实矩阵现象说明：

- `4` 并发时，单任务更快
- `8`、`16` 并发时，总吞吐有提升，但单任务时延明显恶化
- 根因不是“线程控制失效”，而是当前架构把更多完整任务直接塞进同一个共享瓶颈

未来目标场景是：

- `1000` 个 zip
- 单个 zip 大约 `50MB`
- 期望单任务控制在 `20s` 以内，最好 `12s` 以内

因此需要把并发语义从“单一全局线程池”改成“多个标准工作单元横向复制”。

## 2. 目标

本方案目标不是继续把更多线程塞进同一个执行池，而是：

1. 固化 `4` 为标准工作单元
2. 当用户选择 `8/12/16/.../40` 时，通过复制标准工作单元来扩展吞吐
3. 不改变最终转换结果，只改变调度方式
4. 让系统在大批量任务下保持更稳定、更可解释的扩展行为

最终语义定义为：

- `4` = `1` 个标准 worker
- `8` = `2` 个标准 worker
- `12` = `3` 个标准 worker
- `16` = `4` 个标准 worker
- ...
- `40` = `10` 个标准 worker

每个标准 worker 固定只跑：

- `4` 并发

## 3. 核心设计

### 3.1 前端语义

前端不再把并发值表达为“完整任务并发数”，而改为“标准 worker 总量映射值”。

前端约束：

- 只允许选择：`4, 8, 12, ..., 40`
- 不再允许任意整数并发
- 默认值保持为 `4`

前端展示文案应明确说明：

- `4` 表示 1 个工作单元
- `8` 表示 2 个工作单元
- `16` 表示 4 个工作单元

这样用户看到的数值和系统实际调度语义保持一致。

### 3.2 主控进程

主控进程负责：

1. 收集待执行 `TaskPlan`
2. 根据用户选择计算：
   - `worker_unit_size = 4`
   - `worker_count = concurrency / 4`
3. 按数量平均切分任务列表
4. 为每个任务分片拉起一个独立 worker 子进程
5. 汇总 worker 的进度、成功、失败、日志与统计信息

主控进程不再直接把所有任务提交给单一 `ThreadPoolExecutor`。

### 3.3 Worker 子进程

每个 worker 子进程固定配置：

- 内部最大并发 = `4`

每个 worker 负责自己那一片任务，不与其他 worker 共享中间运行空间。

每个 worker 必须拥有独立目录：

- 独立 `adapter_work`
- 独立 `stage_root`
- 独立临时视频目录
- 独立日志目录

这样可以尽量减少：

- 临时目录冲突
- 中间产物相互污染
- 共享 writer 或路径造成的异常

### 3.4 任务切片

任务切片策略已经确定为：

- 按数量平均切片

不做：

- 按 zip 大小估算
- 按预估耗时均衡

原因：

- 当前数据集 zip 大小基本均衡
- 额外建模会增加复杂度和调度开销
- 第一版目标是先把架构语义改对

例如：

- `1000` 个任务，用户选 `16`
- `worker_count = 4`
- 则切成约 `250 + 250 + 250 + 250`

## 4. 接口与行为约束

### 4.1 前端约束

- 最大显示并发改为 `40`
- 步进为 `4`
- 不显示非 `4` 倍数选项

### 4.2 后端约束

- `worker_unit_size` 先写死为 `4`
- 不做自动探测
- 不做运行时自适应调整

### 4.3 结果一致性

本方案必须保证：

- 不改变输入适配逻辑
- 不改变 any4 参数语义
- 不改变统计逻辑
- 不改变输出数据结构
- 不改变 parquet、meta、视频结果内容

允许变化的仅包括：

- 调度方式
- 中间临时目录布局
- worker 级日志和主控聚合日志
- manifest 中新增调度字段

## 5. 实现拆分

### 5.1 主控层改造

需要新增一个“主控调度器”层，负责：

- 根据前端并发值换算 `worker_count`
- 对 `TaskPlan` 列表做平均切片
- 为每个切片启动一个 worker 子进程
- 监听 worker 进度并合并回主界面

### 5.2 Worker 入口

需要新增一个 internal worker CLI 入口，用于：

- 接收任务切片
- 在子进程内执行固定 `4` 并发的转换
- 输出 worker 级结果

源码态和打包态都要支持该入口。

### 5.3 日志与埋点

需要补充两级日志：

1. worker 级日志
   - 各 worker 开始时间
   - 任务数量
   - 完成情况
   - 失败明细

2. 任务级日志
   - 继续保留 `started_at`
   - `finished_at`
   - `elapsed_seconds`

必要时增加：

- `worker_id`
- `worker_index`

用于还原任务属于哪个 worker。

### 5.4 前端进度聚合

前端需要从“单一任务池进度显示”改成：

- 主控总进度
- worker 数量与状态
- 任务明细仍可逐条显示

这样可以避免用户误以为系统仍在串行执行。

## 6. 测试计划

### 6.1 单元测试

需要覆盖：

- `4/8/12/16/40` 正确映射为 `1/2/3/4/10` 个 worker
- 任务列表按数量平均切片
- 任务数不能整除时，切片分配仍然合理
- worker 级别结果能正确汇总回主控

### 6.2 集成测试

需要覆盖：

- 小样本下 `4` 与 `8` 的输出内容一致
- 多 worker 下临时目录彼此隔离
- 一个 worker 失败时，不污染其他 worker 结果
- manifest 中能正确落出任务时间字段与 worker 标识

### 6.3 性能测试

需要至少复测：

- `4`
- `8`
- `16`
- `32`
- `40`

验证指标：

- 总耗时
- 单任务 `P50 / P95`
- 每个 worker 的任务分布
- 是否存在明显空转 worker

### 6.4 验收标准

第一阶段验收标准：

1. `4` 的单任务能力不退化
2. `8/16/32/40` 均通过“复制标准 worker”实现，而不是单池堆线程
3. 输出结果与旧实现保持一致
4. 大批量任务下可以清晰观察到多 worker 分片执行

## 7. 默认假设

本方案采用以下已确认前提：

1. `4` 是当前单机标准 worker 的最优并发值
2. zip 体积和任务规模基本均衡，可直接按数量平均切片
3. 第一版先追求“调度语义正确”，不引入动态负载均衡
4. 第一版不做 `worker_unit_size` 配置化，固定写死为 `4`

## 8. 后续演进

如果第一版落地后验证有效，后续可再考虑：

1. 将 `worker_unit_size` 配置化
2. 增加按机器能力生成推荐配置
3. 增加更强的 worker 级监控
4. 进一步优化前端进度展示，让用户清楚看到：
   - 当前 worker 数
   - 各 worker 已分配任务数
   - 总吞吐变化

## 9. 结论

本方案的核心不是继续扩大单个共享执行池，而是：

- 把 `4` 固化成标准工作单元
- 用多个独立 worker 子进程横向复制这个标准单元

这样可以让未来 `1000` 个 zip 的大规模任务，在不改变最终结果的前提下，获得更稳定、更灵活、也更容易解释的扩展行为。
