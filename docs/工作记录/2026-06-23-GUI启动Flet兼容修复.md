# GUI 启动 Flet 兼容修复

## 问题背景

用户反馈远程下载的 `DataConverterShell-full.exe` 双击无法打开，截图报错为：

```text
module 'flet.controls.padding' has no attribute 'symmetric'
```

此前验证只覆盖了打包 exe 的 `--internal-run-conversion` 内部转换入口，未覆盖 GUI 双击启动链路，因此对 Windows 包可用性的结论不完整。

## 根因分析

本地开发环境的 Flet 仍支持 `ft.padding.symmetric(...)` / `ft.padding.only(...)` 这类模块级 helper。
远程 Windows full 包中打入的 Flet 版本为 class-based API：`flet.controls.padding` 模块只导出 `Padding` 类，
`symmetric` / `only` 是 `ft.Padding` 的类方法，不再是 `ft.padding` 模块函数。

进一步检查发现 `border` 也存在同类差异：远程包中的 `flet.controls.border` 只导出 `Border` 类，
`all` / `only` 是 `ft.Border` 类方法。若只修复 padding，GUI 启动后仍可能继续在 `ft.border.all(...)`
或 `ft.border.only(...)` 处失败。

## 改动方案

在 `src/data_converter/main.py` 增加兼容 helper：

- `_padding_symmetric(...)`
- `_padding_only(...)`
- `_border_all(...)`
- `_border_only(...)`

这些 helper 优先使用旧版模块级 API；若不存在，则回退到新版 `ft.Padding` / `ft.Border` 类方法。
同时将 GUI 构建路径中的 `ft.padding.symmetric/only` 与 `ft.border.all/only` 调用统一替换为兼容 helper。

## 回归测试

在 `test/python/test_main_entry.py` 中新增两个回归测试，使用 fake Flet 对象模拟远程包中的 class-based API：

- `test_padding_helpers_support_class_based_flet_padding_api`
- `test_border_helpers_support_class_based_flet_border_api`

先验证测试在 helper 不存在时失败，再实现兼容层后转绿。

### 根因分析

包体膨胀主要不是 `any4lerobot` 源码本身导致，`any4lerobot` 目录约 0.41 MB；主要来自 PyInstaller 的整包收集策略。

`full`/`onefile`/smoke 打包链路均使用了多处 `--collect-all`：

```text
flet
flet_desktop
ray
torch
lerobot
agibot_utils
psutil
rosbags
```

其中 `torch` 的 Windows wheel 自带大量动态库，单项超过 1GB，是第一优先级。`ray` 使用 `collect-all` 会额外拉入 dashboard、rllib、data、serve、autoscaler、tune、train、llm 等本项目未直接使用的子模块。

`scripts/install_curated_env.ps1` 还额外安装了不在 `pyproject.toml` 中的包：

```text
diffusers
accelerate
cmake
einops
av
pynput
pyserial
wandb
```

旧产物中未发现 `diffusers`、`accelerate`、`cmake`、`einops`、`pynput`、`serial`、`wandb`、`tensorflow`、`tensorflow_datasets`、`datatrove`、`libero`、`robosuite`、`apache_beam` 目录，因此它们在当前旧包里不是主要体积来源。但这些包留在 curated 环境里会增加 PyInstaller 误收集风险、安装耗时和环境复杂度。

### 依赖分层结论

可明确保留：

- `flet` / `flet_desktop`：GUI 必需。
- `h5py` / `numpy` / `opencv-python-headless` / `pillow`：raw 适配、视频/图像处理、Rosbag 转换必需。
- `rosbags`：Rosbag 输出必需。
- `pyarrow` / `jsonlines` / `datasets`：LeRobot v3.0/v2.1/v2.0 元数据和 parquet 后处理仍在使用。
- `lerobot`：`any4lerobot/agibot2lerobot/agibot_h5.py` 顶层依赖 `LeRobotDataset`。
- `av`：`agibot_utils/lerobot_utils.py` 顶层导入，且视频编码链路依赖它或其动态库。

可优先裁剪或降级收集：

- `ray[default]`：项目只需要本地 `ray.init` / `ray.remote` / `ray.get` / `RuntimeEnv`，不需要 dashboard、rllib、serve、autoscaler、tune、train、llm。应优先尝试将安装依赖从 `ray[default]` 改为 `ray`，并把 PyInstaller 从 `--collect-all ray` 改为最小 hidden-import/data 收集。
- `torch`：当前 `agibot_h5.py` 通过懒加载仅用于识别/转换 torch tensor，但 `lerobot` 本身可能间接依赖。可作为高收益专项验证：先移除 `--collect-all torch`，让 PyInstaller 只收分析到的必要二进制；若 LeRobot 运行缺库，再逐项补 hidden-import/binaries。
- `lerobot`：不需要整包策略里的 `policies`、`robots`、`teleoperators`、`rl`、`scripts` 等训练/机器人控制模块。可尝试只收集 `lerobot.datasets`、`lerobot.common.datasets`、`lerobot.utils` 相关模块。
- `tkinter`：主应用是 Flet，源码未直接导入 tkinter。若 Flet Desktop 不要求，可删除 `--collect-data tkinter` 做 smoke 验证。

可从 curated 环境先移除：

- `diffusers`
- `accelerate`
- `cmake`
- `einops`
- `pynput`
- `pyserial`
- `wandb`

这些包在源码静态导入中没有对应业务路径；当前旧产物也未打入对应顶层目录。

暂不建议删除：

- `torchvision`：虽然 AgiBot 当前主路径未直接导入，但 `robomind2lerobot` 工具链中有顶层导入；如果 bundled any4 仍保留全部 upstream 工具目录，贸然删会影响健康检查或未来入口。
- `pandas`：由 `datasets`/版本转换工具链间接使用，旧产物中体积不大，风险收益比不高。
- `huggingface-hub`：版本转换脚本中有导入，且 `lerobot` 生态常依赖。

### 改动建议

本轮仅做审计，未改打包脚本。建议后续分两阶段做：

1. 低风险清理：从 `install_curated_env.ps1` 移除无业务导入的额外包，并确认 `pyproject.toml` 与 curated 环境一致。
2. 打包瘦身专项：优先处理 `ray` 与 `torch` 的 `collect-all`，每次只改一类依赖，重新 `full` 打包并执行依赖校验与真实转换 smoke。

### 当前结论

确实存在可以优化的冗余依赖和过宽收集策略。当前最大问题是 `torch` 和 `ray` 被整包收集；其次是 curated 安装脚本包含多项当前业务未使用的依赖。保守预计，仅优化 `ray` 的安装 extras 与收集范围可以减少几十 MB；若能安全减少 `torch` 整包收集，收益可能达到数百 MB 到 1GB 级别，但需要完整转换 smoke 验证。

### torch 必要性补充确认

用户追问 `torch` 是否必要。本轮复查结果：

- `lerobot==0.4.4` 的包元数据声明依赖 `torch<2.11.0,>=2.2.1`。
- `torchvision==0.17.2` 的包元数据声明依赖 `torch==2.2.2`。
- `any4lerobot/agibot2lerobot/agibot_h5.py` 中通过 `importlib.import_module("torch")` 懒加载 `torch`，用于判断/处理 torch tensor。
- `any4lerobot/ds_version_convert/v16_to_v20/convert_dataset_v16_to_v20.py` 也直接导入并使用 `torch`，但当前主业务路径主要是 AgiBot -> LeRobot v3.0/v2.1/v2.0，不一定会执行 v16_to_v20。

当前判断：`torch` 对 bundled LeRobot 转换运行时是必要依赖，不能简单删除；但 `--collect-all torch` 是否必要仍需专项验证。优化方向应是保留 `torch` 依赖，同时尝试减少 PyInstaller 对 `torch` 的全量收集范围。

## torch 打包收集范围二次瘦身

### 问题背景

用户要求继续把转换器打包产物压到“最小必要依赖”，并且在产物达到最小依赖后，重新验证线程
`019eeee0-341c-7560-b05b-79b9c7f76bc3` 中修复过的问题：

- 平台 `annotation_result.json[action_text]` 不能丢失，不能退化为 `auto-adapted scene`。
- LeRobot 最终 metadata 中的 task 不能带 `task_xxx | ` 或 `test_gaok_xxx | ` 前缀，只保留真实指令。

### 根因分析

上一轮已经确认 `torch` 本身是 LeRobot/torchvision/any4 运行时必要依赖，不能删除。但原打包策略使用
`--collect-all torch`，会把 torch 的数据文件、测试/训练/分布式相关 Python 模块和动态库全部收集进 full 包。

本轮逐步验证了三种策略：

1. `--collect-submodules torch --collect-binaries torch`：可打包、可转换，`_internal` 从 `1591.27 MB` 降到 `824.68 MB`。
2. `--collect-binaries torch --hidden-import torch`：可打包、可转换，尺寸与上一策略一致，且收集语义更窄。
3. 进一步 `--exclude-module torch.testing/torch.distributed/torch.onnx/torch._inductor/torch._dynamo`：打包成功，但真实转换只生成诊断文件，未稳定生成完整 LeRobot 数据集，因此回退。

### 改动方案

最终保留验证通过的最小策略：

```text
--collect-binaries torch
--hidden-import torch
```

同时继续禁止以下过宽收集：

```text
--collect-all torch
--collect-submodules torch
```
