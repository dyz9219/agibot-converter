# 2026-03-20 LeRobot v2.1 图片顺序与图片转换方式对齐记录

## 问题背景
- 用户反馈当前转换到 LeRobot 后，图片顺序需要与原始图片文件顺序完全一致。
- 用户同时要求图片转换方式必须完全借鉴 `E:\Users\dyz\Documents\WXWork\1688858286666779\Cache\File\2026-03\convert_agibot_raw_to_lerobot.py` 的图片处理逻辑，重点参考其 `cv2.imread -> cv2.cvtColor(BGR2RGB) -> resize` 的流程。
- 目标输出主要针对 LeRobot `v2.1` 的 `observation.images.*_color` struct 列。

## 现象分析
- 当前仓库 raw -> any4 适配层 `src/data_converter/adapters/raw_to_any4.py` 只会收集并复制现有 `mp4` 到 any4 输入目录，不会直接读取 `camera/.../color/*.jpg` 原始图片。
- 当前 `src/data_converter/converters/lerobot_runner.py` 在 v2.1 schema 重写时，会从 `mp4` 通过 `cv2.VideoCapture` 反解视频帧，再用 `cv2.imencode('.jpg')` 写入 parquet 的 `struct<bytes,path>` 列。
- 因此旧逻辑存在两个风险：
  - 顺序依赖视频帧顺序与 parquet 行顺序，不保证与原始图片文件名顺序完全一致。
  - 图片颜色与缩放链路没有复用参考脚本的逐图 `imread/cvtColor/resize` 方式。

## 根因分析
- v2.1 后处理阶段缺少“优先使用 raw 图片目录”的分支，导致只要已经生成了 `mp4`，就会默认按视频进行二次解码。
- `frame_index` 与原始图片文件名之间没有建立优先映射，path 字段也无法体现真实图片文件顺序。
- 参考脚本的核心行为不是“从视频抽帧”，而是“按图片文件序列直接读图并 resize 后写入数据集”。

## 改动方案
- 修改 `src/data_converter/converters/lerobot_runner.py`：
  - 给 `_embed_videos_in_parquet` / `_embed_dataset_videos_in_parquet` / `_rewrite_v21_episode_parquet_schema` 增加 `raw_source_dir` 透传能力。
  - 在 `run_lerobot_task` 的后处理阶段，当输入类型为 `raw` 时，把 `source_dir` 作为 `raw_source_dir` 传入 v2.1 图片重写流程。
  - 新增 raw 图片优先读取逻辑：
    - 根据 `episode_index` 定位 raw episode 目录。
    - 按 `camera/head_color/color/*.jpg|png`、`camera/hand_left/color/*`、`camera/hand_right/color/*` 的文件名数值顺序读取图片。
    - 复用参考脚本的处理方式：`cv2.imread` 读取、`cv2.cvtColor(..., cv2.COLOR_BGR2RGB)` 转 RGB、按 head/hand 目标尺寸 resize。
    - 使用 `Pillow` 将处理后的 RGB 图编码为 JPEG bytes，写回 `struct<bytes, path>`。
  - 当 raw 图片目录不可用时，仍保留原有 mp4 解码回退路径，避免影响 any4 输入或非 raw 场景。
- 修改 `test/python/test_lerobot_v21_schema_rewrite.py`：
  - 新增 raw 图片优先测试。
  - 校验 `path` 顺序跟随原始图片文件名 `00000002/00000005/00000009`。
  - 校验解码后的图片尺寸与通道主色，确认转换链路为 RGB + resize，而不是简单沿用旧视频字节。

## 追加：面向 OpenPI 无改动兼容的图片特征元数据修复
- 用户提供 OpenPI 报错：`RuntimeError: Could not infer dtype of dict`
- 结合堆栈分析，根因不是 `state/actions` 数值错误，而是图片列被 loader 当成普通 `dict(bytes,path)`，最终在 `torch.tensor(dict)` 处失败。

### 分析结论
- `datasets.Image` 底层存储类型本身就是 `struct<bytes: binary, path: string>`，所以我们现在的图片列物理结构并不违背 HF datasets 约定。
- 真正缺失的是 parquet schema 里的 HuggingFace feature metadata：
  - 没有 metadata 时，`Dataset.from_parquet(...)` 读出的是：`{'bytes': ..., 'path': ...}`（普通 dict）
  - 补上 metadata 后，同样的列会被识别为 `Image(mode=None, decode=True)`，读取样本时直接得到 `PIL.JpegImageFile`
- 因此，如果目标是“整条 OpenPI 链都不改代码直接兼容”，则**必须调整转换数据**，但重点是：
  - 不是再改图片 bytes/path 结构
  - 而是给 parquet 写入 HF `Image` 特征元数据

### 本轮改动
- 修改 `src/data_converter/converters/lerobot_runner.py`：
  - 新增 `_apply_hf_image_feature_schema()`
  - 在 v2.1 parquet 重写完成后，为三路图片列写入 HuggingFace `Image()` feature metadata，再落盘 parquet
