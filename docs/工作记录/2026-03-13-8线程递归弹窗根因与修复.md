# 2026-03-13 8并发递归弹出EXE窗口根因修复

## 1. 问题背景

人工测试确认：

- `4` 线程在本地稳定，`15` 个 zip 约 `48s` 完成
- 当切到 `8` 线程时，会不断弹出新的 `DataConverterShell-full.exe` 界面

该问题只在新的多 worker 架构下出现，属于严重可用性缺陷：

- 用户期望的是后台扩展并行度
- 不应看到额外 GUI 窗口，更不应递归拉起 EXE

## 2. 现象与调查范围

本轮按 `systematic-debugging` 做了根因调查，先确认多线程/多进程链路：

1. `concurrency >= 8` 时，LeRobot 多任务会进入 `worker shard` 路径
2. 冻结态 EXE 会通过：
   - `--internal-run-worker-shard`
   拉起新的 `DataConverterShell-full.exe`
3. 每个 worker shard 进程内部，再进入：
   - `ProcessPoolExecutor(mp_context=spawn)`
   固定 `4` 并发跑任务

也就是实际链路为：

- 主 GUI EXE
- worker shard EXE
- worker 内部 `spawn` 子进程

## 3. 根因分析

### 直接根因

冻结态 Windows GUI EXE 在入口处没有调用：

- `multiprocessing.freeze_support()`

而 `8` 线程路径恰好会在冻结子进程内部再次使用：

- `ProcessPoolExecutor`
- `spawn`

这会导致新子进程重新进入冻结程序主入口，而不是只进入 multiprocessing 的受控 worker 引导逻辑。

结果就是：

- 子进程错误地重走 `main.py` 主入口
- GUI 路径被重新执行
- 持续弹出新的 `DataConverterShell-full.exe` 窗口

### 为什么 4 线程没问题

`4` 线程时通常仍走单层并发，不会进入：

- 外层 worker shard EXE
- worker 内部再 `spawn` 进程池

因此没有触发这条“冻结 EXE 再次 spawn”的递归入口问题。

### 为什么之前测试没发现

现有测试覆盖了：

- worker shard 命令拼接正确
- worker 模式会使用 `ProcessPoolExecutor`

但没有覆盖：

- 冻结态入口是否先执行 `freeze_support()`
- 冻结态 worker shard 内再次 spawn 时是否会误进 GUI

所以源码模式和 mock 测试都能通过，打包 GUI EXE 才暴露问题。

## 4. 改动方案

修改文件：

- `src/data_converter/main.py`
- `test/python/test_main_entry.py`

具体修改：

1. 将启动逻辑抽成：
   - `run_cli_entry()`
2. 在最外层入口第一时间调用：
   - `multiprocessing.freeze_support()`
3. 保留原有 internal CLI 分流：
   - `--internal-run-any4lerobot`
   - `--internal-run-worker-shard`
   - 其他 internal flags
4. 仅在不属于 internal CLI 时才启动：
   - `ft.app(target=main)`
5. 新增回归测试，验证：
   - `freeze_support()` 先于 worker shard 分流执行
   - `freeze_support()` 先于 GUI 启动执行

## 5. 验证方式与结果

执行命令：

```powershell
pytest -q test\python\test_main_entry.py test\python\test_backend_concurrency.py
```

结果：

- `18 passed in 2.37s`

说明：

- 新入口测试通过
- 原有 worker shard / 并发路径测试未回归

## 6. 当前结论

本次“8 线程无限弹 EXE 窗口”的根因不是任务分片策略本身，而是：

- 冻结态 Windows GUI EXE 在多进程 `spawn` 路径上缺失 `freeze_support()`

这属于启动链路问题，不是转换逻辑问题。

修复后，架构仍可保持为：

- 以 `4` 为标准并发单元
- `8/12/16/...` 通过多个 worker 复制扩展

但 worker 内再 spawn 时不会继续误拉起 GUI 窗口。

## 7. 量化结果与下一步建议

本轮主要是功能性修复，量化结果以“是否阻止递归弹窗”为主；单机吞吐指标需重新对打包产物做一次 smoke 验证。

建议下一步：

1. 重新打 `full` 包
2. 在打包产物上复测：
   - `concurrency=8`
   - `concurrency=16`
3. 重点观察：
   - 是否仍出现额外 GUI 窗口
   - `manifest.json` 与 `.worker-results` 是否正常生成
   - 总耗时是否与源码模式预期接近

## 8. 备注

本轮编辑时 `apply_patch` 工具出现沙箱刷新失败，因此改用一次性脚本完成等价文件写入；修改范围已通过 pytest 回归验证。
