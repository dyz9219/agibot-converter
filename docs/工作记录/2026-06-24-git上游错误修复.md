# 2026-06-24 Git 上游错误修复

## 问题背景

仓库出现大量 `Isaac Downloader` 相关文件，包含 `app.go`、`main.go`、`go.mod`、`frontend/`、`backend/downloader.go`、`go1.23.6*.tar.gz` 等。这些文件不属于当前 `agibot-converter` Python 转换器项目。

## 根因分析

当前仓库曾同时配置两个远端：

- `origin`: `https://github.com/dyz9219/agibot-converter.git`
- `gitlab`: `http://172.16.40.101:8888/isaac-sim/downloader.git`

更关键的是，`branch.main.remote` 被错误配置为 downloader 仓库 URL：

```text
branch.main.remote http://dengyangzhi:***@172.16.40.101:8888/isaac-sim/downloader.git
branch.main.merge refs/heads/main
```

因此在当前转换器仓库执行普通 `git pull` 时，Git 拉取并尝试合并的是 `isaac-sim/downloader.git` 的 `main` 分支，而不是 `agibot-converter` 的 `origin/main`，从而产生跨项目合并冲突和大量 downloader 文件。

## 改动方案

- 将 `main` 分支上游改回 `origin/main`；
- 删除错误的 `gitlab` 远端，避免后续误拉 downloader 仓库；
- 执行 `git merge --abort` 中止错误合并；
- 删除错误合入后残留的 downloader 未跟踪文件。

## 量化结果

- 修正分支上游：1 个，`main -> origin/main`
- 删除错误远端：1 个，`gitlab`
- 中止错误 merge：1 次
- 清理 downloader 残留文件/目录：27 项

## 验证方式

- `git config --get-regexp "^remote\\..*\\.(url|fetch)$|^branch\\.main\\.(remote|merge)$"`
- `Test-Path .git\\MERGE_HEAD`
- `git status --short --branch --ignored`

## 当前结论

当前 `main` 已恢复跟踪 `origin/main`，错误 merge 已结束，`Isaac Downloader` 文件已从工作区清理。工作区只剩本地忽略项，例如 `.venv/`、`.idea/`、`.worktrees/` 以及当前 `.gitignore` 忽略的部分 `test/python/test_*.py`。

## 下一步建议

后续在该仓库中执行拉取时，使用 `git pull origin main` 或确认 `git status --branch` 显示 `main...origin/main`。不要在同一仓库中保留无关项目远端，尤其不要把当前分支上游配置到其他项目仓库。

# 2026-06-24 Windows full 产物公开命名调整

## 问题背景

GitHub Actions 的 Windows full 打包产物对外名称仍带 `full`：

- artifact 名称：`DataConverterShell-Windows-full`
- dist 目录与 exe 名称：`DataConverterShell-full/DataConverterShell-full.exe`

用户要求 Windows 每次打包本来就是 full，因此对外发布命名去掉 `full`，但内部仍保留 `-Profile full` 作为构建模式。

## 根因分析

full/fast 原本同时体现在构建 profile 和对外发布文件名里。当前 Windows 发布只分发 full 包，继续把 `full` 放进 artifact、目录和 exe 名称会造成冗余，也让下载后的主程序名不够稳定。

本地验证时还发现 `verify_build_fingerprint.ps1` 会把 `DataConverterShell.spec` 纳入源码指纹，但该 spec 会被 PyInstaller 在打包过程中重新生成，导致同一次构建后校验当前工作区时出现指纹不一致。

下载 GitHub Actions 产物到本地验证时，又发现 GitHub checkout 的脚本换行通常为 LF，而本机工作区为 CRLF；若指纹按原始字节计算，同一提交的远端 clean 包会在本地出现 `source_fingerprint mismatch`。因此指纹计算需要对文本换行做稳定化。

## 改动方案

- Windows full profile 输出目录改为 `dist/DataConverterShell`；
- Windows full profile exe 名称改为 `DataConverterShell.exe`；
- GitHub Actions artifact 名称改为 `DataConverterShell-Windows`；
- workflow 中 any4 校验与构建指纹校验路径同步改为新路径；
- `verify_build_fingerprint.ps1` 默认 full exe 路径同步改为新路径；
- 删除旧的 `DataConverterShell-full.spec`；
- 新增测试覆盖旧公开命名不得回归；
- 将构建指纹口径改为稳定输入：`src/data_converter` 与 `scripts/build_exe.ps1`，不再包含生成型 `DataConverterShell.spec`；
- 构建指纹计算统一将 CRLF 归一为 LF，保证 GitHub clean checkout 与 Windows 本地工作区可以交叉校验。

## 量化结果

- Windows artifact 公开名：`DataConverterShell-Windows-full` -> `DataConverterShell-Windows`
- Windows exe 公开名：`DataConverterShell-full.exe` -> `DataConverterShell.exe`
- Windows dist 目录：`dist/DataConverterShell-full` -> `dist/DataConverterShell`
- 包装依赖测试数量：4 个 -> 6 个
- 本地 full 打包 exe 大小：`58,978,536` bytes

## 验证方式

- `pytest -q test\python\test_packaging_dependencies.py`
  - 结果：6 passed
- `pytest -q test\python`
  - 结果：65 passed, 6 skipped
- `.\scripts\build_exe.ps1 -Profile full -Clean`
  - 结果：生成 `dist\DataConverterShell\DataConverterShell.exe`
- `.\scripts\verify_packaged_any4.ps1 -DistRoot dist\DataConverterShell`
  - 结果：`OK: packaged any4 matches repo source.`
- `.\scripts\verify_build_fingerprint.ps1 -ExePath dist\DataConverterShell\DataConverterShell.exe`
  - 结果：`FINGERPRINT_CHECK_OK`
- `dist\DataConverterShell\DataConverterShell.exe --internal-build-info`
  - 结果：`profile=full`，`git_dirty=true`，可读出构建元信息
- `dist\DataConverterShell\DataConverterShell.exe --internal-run-rosbag-health --bag-type MCAP`
  - 结果：`ROSBAG_HEALTH_OK`
- `dist\DataConverterShell\DataConverterShell.exe --internal-run-any4-health --version v3.0`
  - 结果：exit code 0
- 使用 `task_2059925964389343234.zip` 本地执行 LeRobot v3.0 转换：
  - `codebase_version`: `v3.0`
  - 数据行数：460
  - episode task：`把瓶子放进筐子里`
  - 未出现 `auto-adapted scene`
  - 未出现 `task_xxx | ` 前缀

## 当前结论

本地 full 打包产物已经改为不带 `full` 的公开名称，同时保留 `-Profile full` 构建模式。包内 any4、构建指纹、rosbag health、any4 health 与真实 zip 转换均已通过本地验证。

## 下一步建议

提交并推送到 GitHub 后，需要等待 Actions 生成新的 `DataConverterShell-Windows` artifact，再下载 zip 验证其中根目录与 exe 均不带 `full`，并复跑同一个真实 zip 转换 smoke。

# 2026-06-24 Linux x64 artifact 体积继续偏大分析与修复

## 问题背景

最新 GitHub Actions 中 `DataConverterShell-Linux-x64` artifact 仍约 `897,948,092` bytes，明显高于 `DataConverterShell-Linux-ARM64` 的约 `319,429,710` bytes，也高于 Windows artifact 的约 `299,424,353` bytes。用户要求查询原因并修复。

## 根因分析

Linux x64 workflow 仍使用 `PyInstaller --onedir`，上传路径为 `dist/DataConverterShell/`，因此 artifact 中包含目录型分发产物。Linux ARM64 已使用 `--onefile` 并上传 `dist/DataConverterShell` 单文件，体积明显更小。

历史上 Linux x64 曾因默认 GPU PyTorch / CUDA 依赖导致 `--onefile` 触发 PyInstaller CArchive 4GB 上限，所以临时改为 `--onedir`。当前依赖已切到 CPU torch，并且打包参数已从 `collect_all('torch')` 收敛为只收集 torch 动态库，原先的 4GB 前提已不成立；继续保留 `--onedir` 就成了体积偏大的根因。

第一轮改成 `--onefile` 后，GitHub Actions 验证通过，但 `DataConverterShell-Linux-x64` 仍为 `640,975,107` bytes。进一步查看 x64 job 日志发现：通用依赖安装命令里包含 `accelerate>=1.10.0,<2.0.0`，而 CPU torch 是下一条命令才安装。因此 pip 在第一轮先从 PyPI 拉取了满足 `torch>=2.0.0` 的 Linux x64 torch（日志出现 `torch-2.12.1`），之后再用 CPU `torch==2.2.2` 覆盖 torch 本体，但第一轮带入的大依赖残留仍可能被 PyInstaller 收集（日志中出现 `triton/_C/libtriton.so`）。

## 改动方案

- 将 `build-linux-x64` 的 PyInstaller 参数从 `--onedir` 改回 `--onefile`；
- 同步修改 Linux x64 smoke 命令，从 `./dist/DataConverterShell/DataConverterShell` 改为 `./dist/DataConverterShell`；
- 同步修改 Linux x64 artifact 上传路径，从 `dist/DataConverterShell/` 改为 `dist/DataConverterShell`；
- 将 Linux x64 CPU `torch==2.2.2` / `torchvision==0.17.2` 安装提前到通用依赖安装之前，避免 `accelerate` 先触发 PyPI torch 解析；
- 新增测试保证 Linux x64 不再回退到目录型 artifact，并保证 CPU torch 安装顺序早于 `accelerate`。

## 量化结果

- 修复前 GitHub artifact 大小：
  - `DataConverterShell-Linux-x64`: `897,948,092` bytes
  - `DataConverterShell-Linux-ARM64`: `319,429,710` bytes
  - `DataConverterShell-Windows`: `299,424,353` bytes
- 第一轮 `--onefile` 后 x64 artifact：`640,975,107` bytes
- 包装依赖测试数量：6 个 -> 8 个

## 验证方式

- `pytest -q test\python\test_packaging_dependencies.py`
  - 结果：8 passed
- `pytest -q test\python`
  - 结果：67 passed, 6 skipped

## 当前结论

Linux x64 zip 偏大的原因分两层：第一层是 x64 job 仍在上传 `--onedir` 目录型产物；第二层是安装顺序让 `accelerate` 先触发 PyPI torch 解析，可能留下大体积依赖残留。已改为 `--onefile` 单文件产物，并让 CPU torch 先安装。最终体积需要以 GitHub Actions 重新构建后的 artifact 元数据为准。

## 下一步建议

推送后等待新的 GitHub Actions run 完成，确认 `build-linux-x64` 在 `--onefile` 下不再触发旧的 4GB CArchive 问题，也不再提前拉取 PyPI torch，并记录新的 `DataConverterShell-Linux-x64` artifact size。
