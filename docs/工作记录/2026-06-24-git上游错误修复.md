# 2026-06-24 Windows full 产物公开命名调整

# 2026-06-24 Linux x64 artifact 体积继续偏大分析与修复

## 问题背景

最新 GitHub Actions 中 `DataConverterShell-Linux-x64` artifact 仍约 `897,948,092` bytes，明显高于 `DataConverterShell-Linux-ARM64` 的约 `319,429,710` bytes，也高于 Windows artifact 的约 `299,424,353` bytes。用户要求查询原因并修复。

## 根因分析

Linux x64 workflow 仍使用 `PyInstaller --onedir`，上传路径为 `dist/DataConverterShell/`，因此 artifact 中包含目录型分发产物。Linux ARM64 已使用 `--onefile` 并上传 `dist/DataConverterShell` 单文件，体积明显更小。

历史上 Linux x64 曾因默认 GPU PyTorch / CUDA 依赖导致 `--onefile` 触发 PyInstaller CArchive 4GB 上限，所以临时改为 `--onedir`。当前依赖已切到 CPU torch，并且打包参数已从 `collect_all('torch')` 收敛为只收集 torch 动态库，原先的 4GB 前提已不成立；继续保留 `--onedir` 就成了体积偏大的根因。

- 同步修改 Linux x64 artifact 上传路径，从 `dist/DataConverterShell/` 改为 `dist/DataConverterShell`；
- 将 Linux x64 CPU `torch==2.2.2` / `torchvision==0.17.2` 安装提前到通用依赖安装之前，避免 `accelerate` 先触发 PyPI torch 解析；

## 量化结果

  - `DataConverterShell-Linux-ARM64`: `319,429,710` bytes

  - 结果：8 passed

  - 结果：67 passed, 6 skipped

Linux x64 zip 偏大的原因分两层：第一层是 x64 job 仍在上传 `--onedir` 目录型产物；第二层是安装顺序让 `accelerate` 先触发 PyPI torch 解析，可能留下大体积依赖残留。已改为 `--onefile` 单文件产物，并让 CPU torch 先安装。最终体积需要以 GitHub Actions 重新构建后的 artifact 元数据为准。

- `./dist/DataConverterShell --internal-run-any4-health --version v2.1`
- `./dist/DataConverterShell --internal-run-any4-health --version v2.0`

因此问题不在 PyInstaller 产物本身的启动能力，而更可能发生在 CI 验证之后、用户下载 artifact 之后的分发边界。

## 根因分析

当前 workflow 在 CI 中先执行 `chmod +x dist/DataConverterShell`，随后直接用 `actions/upload-artifact@v4` 上传裸 `dist/DataConverterShell` 文件。GitHub artifact 下载为 zip 包，zip 解包后的 Linux 文件权限通常不会保留原始执行位，用户拿到的 `DataConverterShell` 可能变成普通 `0644` 文件，直接执行会失败。

这解释了现象差异：

- CI 内部 smoke 能过：因为上传前已 `chmod +x`；
- 用户下载后不能正常使用：因为 artifact zip 边界丢失执行权限。

## 改动方案

- `build-linux-x64` 不再直接上传裸 ELF 文件；
- 先执行 `tar -czf dist/DataConverterShell-Linux-x64.tar.gz -C dist DataConverterShell`；
- 在 CI 中立刻解包到 `/tmp/agibot-linux-x64-package-check`，用 `test -x` 验证执行位仍保留；
- 再运行解包后的 `DataConverterShell --internal-build-info`，确认 tar 包里的实际交付物可启动；
- 同步给 `build-linux-arm64` 做同样包装与验证，避免两个 Linux 产物分发方式继续分叉；
- 更新 `test/python/test_packaging_dependencies.py`，断言 Linux x64/ARM64 必须上传 `.tar.gz`，并必须检查解包后的执行位。

## 量化结果

本地静态测试结果：

- `pytest -q test/python/test_packaging_dependencies.py`
  - 结果：`9 passed in 0.13s`

本轮没有重新构建 Linux 二进制；最终 artifact 体积与下载后权限需要等待下一次 GitHub Actions run 验证。

## 当前结论

Linux x64 “构建时能跑、下载后不能正常使用”的根因定位为 artifact 分发格式没有保留 Linux 执行权限。已改为上传 `.tar.gz` 并在 CI 中验证解包后执行位，验收标准从“CI 中裸文件可执行”提升为“最终压缩包解出后可执行”。

## 下一步建议

推送后观察新的 GitHub Actions run，重点确认：

- `build-linux-x64` 的 `Package Linux artifact` 步骤通过；
- artifact 内包含 `DataConverterShell-Linux-x64.tar.gz`；
- 在干净 Linux x64 机器下载并 `tar -xzf` 后，`./DataConverterShell --internal-build-info` 可直接运行。
